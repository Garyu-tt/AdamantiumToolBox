# Client Device Watchdog R01 (CPU-first)

This module is an **optional backend-only** MAS application, not a GUI and
not another JediControl implementation. It consumes a local diagnostic state
file generated by an independent Windows task guardian. It does not expose
shell, input, task start or tunnel controls via MAS.

## Components

- `apps/client_watchdog`: local read-only MAS app with
  `client_watchdog.status`, governed by `client_watchdog.read` permission.
  Authenticated Core /api/invoke is the only intended action gateway.
- `tools/windows-client-watchdog.ps1`: separate user-context Windows
  process observing pre-registered Scheduled Tasks. Writes a small local
  diagnostic snapshot. Optional auto-start applies only when explicitly
  enabled per target and only to stopped, least-privilege, same-user tasks.
  It does not terminate a running task or bypass UAC.
- `standards/client-watchdog/config.example.json`: example only. No client
  endpoints, passwords, SSH identities or bearer tokens are committed.

Status fields: `mode` is `fresh`, `stale`, `not_configured` or `invalid`.
`targets` contain only id, task-running flag, opt-in probe result, failure
count, reason, last successful check, and last restart attempt. These are
**local observations**, not proof of remote node identity, a live desktop,
or an approved ChatGPT control lease.

## Owner-local opt-in

1. Review the exact target Task Scheduler name and ownership on the laptop.
   Never target the interactive desktop agent or elevated/UAC helper.
2. Copy the example to
   `%LOCALAPPDATA%\Adamantium Toolbox\client-watchdog\config.json`
   and adjust only approved transport/service tasks. No secrets in config.
   Set `autoStart:true` **only** when a stopped task is safe to restart
   without local consent. The default is false.
3. Run `powershell.exe -NoProfile -File tools\windows-client-watchdog.ps1 -Once`
   for an interactive dry observation. Run without `-Once` only after
   reviewing Task Scheduler execution at user logon. No task is registered,
   activated or installed automatically by this PR.
4. Grant `client_watchdog.read` locally through the existing owner policy
   if remote diagnostic consumption is desired. Existing policies are not
   overwritten. A local Hub status does not make an MCP ingress reachable.

For targets with `healthUrl`, probes accept trusted HTTPS (normal certificate
validation) or HTTP on loopback only, without query strings, userinfo or
redirects. The probe must check the actual authenticated session, not merely
that an SSH process or a TCP listener exists, to detect a stuck tunnel.
The sample loopback URL is a placeholder and MUST be replaced.

The guardian checks every 5..300 seconds; optional Task Scheduler starts
require consecutive failures and at least 30 seconds cooldown. Cooldown
state persists in a local status file across process restarts. There is
a single-instance mutex. It cannot revive a sleeping/powered-off laptop,
and an already-running but broken transport requires a transport-specific
adapter to repair itself. The local script never force-stops such a task.

## Safety and lifecycle

Service runs in caller's user context; OS task controls require local rights.
JediControl emergency latch, remote controller lease, local UAC and device
identity must be enforced by their own separate adapters. Do not configure
this generic task starter to override those decisions. No public listener,
external remote shell, raw credentials or silent privilege elevation.
The app's HTTP socket binds loopback. It is not the external MCP gateway.

## Acceptance gates

- `node tests/client_watchdog.test.mjs` verifies Core + headless app,

- Windows PowerShell syntax check in CI. Real Task Scheduler behavior,
  sleep/wake, Wi-Fi roaming, user logoff and 24-hour soak require a
  separately approved laptop acceptance run before deployment.
